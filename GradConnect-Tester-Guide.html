Getting set up

Run with Docker

GradConnect ships as a self-contained Docker stack, so you don't need to install PHP, Node, or PostgreSQL — only Docker Desktop. The whole app (web server, database, and background worker) starts with a single command.

1 · Install Docker Desktop

Download and install Docker Desktop for your operating system, launch it, and wait until the whale icon is steady (the engine is running). On Windows, keep the WSL 2 option enabled if prompted, and let it finish its first-time setup before continuing.

2 · Get the project & start it

Open a terminal (PowerShell on Windows) and run these four commands:

git clone https://github.com/hernancpanaguiton-glitch/gradconnect.git cd gradconnect cp .env.docker.example .env.docker docker compose up --build

The first build takes a few minutes — it downloads the images and compiles the front-end. It's ready when the log shows Server running on [http://0.0.0.0:8000].

3 · Open the app

Visit http://localhost:8000 in your browser and sign in with one of the accounts in the next section.

Registering your own account The sign-up form now asks for a role. Student and Alumni accounts are activated right away but must confirm a verification email — open the mail inbox at http://localhost:8025 to find it and click the link. Alumni Officer, Dean, Industry Partner, and Student Affairs Office accounts are held for admin approval: sign in as the Admin below and set the account to active on the Users page before it can log in. Admins are notified in-app and by email when a new account needs approval.
First launch sets everything up for you Database migrations run and demo data is seeded automatically on the first boot — accounts, job postings with applications at every stage, résumés with their AI match results, tracer and readiness survey responses, events with RSVPs, scholarships, clearance records, student concerns, community threads, announcements, and the learning-resource catalogue. Every screen has something real on it; you should not meet an empty page anywhere. The background queue worker runs as its own container, so résumé uploads and the Refresh buttons process live — no extra commands needed.
Enabling live AI matching (optional) The alumni@ account already shows pre-generated AI recommendations you can view immediately. To score new résumé uploads or the Refresh recommendations / Refresh matches buttons, paste the shared Gemini & Groq keys into .env.docker (GEMINI_API_KEY, GROQ_API_KEY), then restart: docker compose down then docker compose up. Without keys, uploads still save but stay unscored.

Handy commands

docker compose up -d # run in the background docker compose logs -f app # watch the app logs docker compose down # stop the app (keeps your data) docker compose down -v # stop and wipe data for a clean restart
Stuck on a seeding / "duplicate key" error? That means a previous run left half-seeded data. Reset with docker compose down -v (the -v wipes the database), then docker compose up --build for a clean start.

Common ground

What every role gets

These six features are on every account regardless of role — what they show changes with your permissions. The role sections that follow list only what is specific to that role, so check here first if you're wondering where something lives.

Set expectations

Known gaps — not bugs

Every sidebar link in every role now resolves to a real, data-backed screen — there are no design-shell placeholders left, and no demo/sample data hardcoded in the UI. What remains below are environment requirements and deliberate design decisions, not defects:

  • A queue worker must be running for résumé embeddings, AI match scoring, and all notification email. Use composer dev (which runs one alongside the server) or docker compose up (which has a dedicated worker container). Without it these silently stay pending — Admin → Platform Status will tell you if the queue has stalled.
  • Live AI scoring needs API keys. With GEMINI_API_KEY and GROQ_API_KEY set, matches are embedded and scored for real. Without them the seeded match results still display, so recommendations and skill-gap analysis remain demonstrable.
  • Backups need the PostgreSQL client tools. Admin → Data & Backups shells out to pg_dump; if it isn't on the server's PATH the page says so plainly. Restoring is intentionally command-line only (php artisan backup:restore), since it overwrites the live database.
  • Department Heads see employment and program data scoped to their own college, by design — the filters are locked to their department rather than offered institution-wide.
  • Employers can view any graduate's profile through Talent Search, but can only open the résumé file of someone who actually applied to one of their own postings.
  • Admin → Platform Status deliberately shows no response-time metric: the app has no request-timing instrumentation, so that number would be invented rather than measured.
  • Self-registration assigns the chosen role immediately. Student and Alumni accounts activate right away (email verification still required); every other role (Alumni Officer, Dean/Department Head, Industry Partner, SAO) is created with a role but a pending status until an Admin approves it under User Management. For testing, use the seeded logins above.
  • This is a responsive web application, not a native mobile app — that boundary is stated in the study's scope.

Found a real issue? Note the role, the page, and what you expected vs. saw — that's enough to reproduce it quickly.
